> 日期: 2026-09-19 · 侦察工具: `hook_export_trace.js` + `re_probe_p1.py` (commit 14201dc)
> 数据: 渲染节点 6 轮侦察, 产出在 Linux `/tmp/p1probe/out*/`
> 结论: **函数级导出成立, 入口已锁定, 请求结构已画出主字段**

## 1. 渲染启动真相 (时间线实锤)

```
点导出按钮 → 导出面板打开 → ExportClient::exportStart 立即触发 (silent_export)
          → CreateFileW 创建 .__jianying_export_temp_folder__\<uuid>.mp4
          → ttvideoeditor.dll (Vulkan) + avformat-58 (FFmpeg) 渲染进行中
点确认导出 → 仅收尾确认 (渲染已在后台跑)
渲染完成   → temp 改名到 Videos\<draft>.mp4
关闭编辑器 → exportStart 再次触发 (第二次, 收尾阶段)
```

- 真实渲染入口 = `ExportClient::exportStart`（`videoeditor.dll` 导出符号, mangled 名可按名定位）
- 调用点恒定: `VECreator.dll+0x3040444`
- `NewVEWrapper::export_start` 存在但 UI 流程不经过它 (待利用的替代入口)
- 真实编码引擎 = `ttvideoeditor.dll` (626 导出, 纯 Vulkan vkCmd* 后端) + FFmpeg libavformat-58 (`Lavc61.31.101`)

## 3. P2 施工方案 (按风险递增排序)

- **A. 飞行中补丁 (最低风险)**: hook exportStart onEnter, 改写 +0x50 输出路径字符串后放行 → 完全控制输出位置, UI 链路不动
- **B. 请求克隆重放**: 首次触发时深拷贝请求 (含指针目标内存), 同会话内再调用 `ExportClient::exportStart` 重放 → 一次 UI 交互, N 次渲染
- **C. 全构造直调**: 从零构造 ExportStartReqStruct (跳过导出面板点击) — 需弄清混淆 token 区 (疑签名) 是否可复用, 风险最高
- 建议顺序 A → B → C, 每步在 probe 环境验证后再进 render_driver

## 6. P2-A 飞行中补丁实验结果 (2026-09-19 晚, 3 轮节点实验)

### 实验记录
| 轮次 | 补丁目标 | 结果 |
|---|---|---|
| A1 | 两次 exportStart 都补丁到独立目录 `.__jianying_probe_out\p1_patched.mp4` | 引擎**确实写到补丁路径** (15,898,472 B 完整成片); 但 app 收尾按预持路径搬运找不到文件 → exportCancel + 自动重试(路径变 Videos\<uuid>.mp4) → 重试也被补丁 → 成片失踪 → 驱动超时 |
| A2 | 只补丁含 temp_folder 的请求(静默预渲染), 放过重试请求 | 完美: `p1_patched.mp4` 全尺寸成片落在补丁路径 **且** app 正常交付 rd*.mp4, exit=0 |

### 机制实锤
- **引擎写盘位置 = 请求 +0x50 字符串, 原位补丁(≤cap 覆盖)完全生效**
- **成片改名交付用 app 预持路径副本, 不读请求字符串** → 补丁交付类请求(#3, Videos\<uuid>)会断成片
- **确认点击的真实语义** = exportCancel(取消静默预渲染) + exportStart#3(Videos\<uuid>.mp4 真实交付请求) → 改名 rd<ts>.mp4
- **静默预渲染本身即完整成片** — 不点确认它也会渲染完 (补丁路径产物两次全尺寸实锤)

### P2-A 生产形态 (P3 集成方案)
```
注入草稿 → 打开草稿 → 点一次"导出"按钮
  → exportStart#1 onEnter 补丁 +0x50 → 任务输出路径
  → 驱动监视补丁路径至大小稳定 (代替确认/完成弹窗点击)
  → ESC 清弹窗 → 关编辑器 → 交付补丁路径成片
```
消掉确认弹窗+完成提示两次最脆交互; 交付不依赖 app 默认目录/改名逻辑.
遗留验证: 不点确认时预渲染是否必然完整跑完 (A1/A2 旁证低风险, P3 实测).

## 11. P1c/P1d — C 方案(零点击装载)判定: 不可行

- P1c: 静态定位 0x1da160 (exportStart/exportCancel 共同尾调链 0x877d0→0x1da160,
  sid==-100 哨兵), 运行时实锤为 **VeWrapper 方法调用层** (setFps/setCanvasSize/
  registerPlayerStatus/exportStart 等方法名过境), 点卡片时无 DraftInit 消息.
- P1d: convert_to_runtime_draft 返回的 Persistent/Draft 指针登记追踪, 在
  draftTransaction/draftCombo/doInitVeWrapper/MixedClient/exportStart 等十函数
  参数(含一级解引用)中零命中 → Draft 指针经 VMProtect 内联闭包安装, 无函数边界.
- 结论: 草稿安装无可调用边界, C 方案封卷. 每渲染 2 次控件点击 (替身卡+导出) 为
  5.9 架构下最优点.
- 下一赛道: ① render_service 常驻剪映会话 (省每任务 35-40s 启动开销, 吞吐翻倍);
  ② P4 输出验收门禁 (精确帧数/全解码).
