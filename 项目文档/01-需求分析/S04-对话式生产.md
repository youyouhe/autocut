## 一、系统概述

### 1.1 系统定位

S04 对话式生产是 AI 视频工作台的"自然语言生产线入口"。用户在 Web GUI 对话面板输入一句话（如"帮我把这个视频配个标题并渲染"），系统将请求经 `/api/chat` 端点以 SSE（Server-Sent Events）流式协议转发至通义千问 qwen3.7-plus（EXT-02），由 LLM 通过 Function Calling 机制自主决策并依次调用资源查询、草稿编辑、渲染提交等工具，把"上传素材 → AI 感知 → 组装草稿 → 无人值守渲染"的整条流水线压缩为一次对话交互。

系统不自行实现任何编辑或渲染能力，而是作为**对话编排层**：向下组合 S01 素材库、S02 感知缓存、S05 草稿编辑服务、S06 无人值守渲染的既有 REST 端点，向上向前端 GUI（S07-005 对话面板）提供统一的流式对话通道。对话期间产生的 `draft_id` 作为会话上下文贯穿多轮，支撑"创建 → 修改 → 续编 → 渲染"的连续生产。

| S04-003 | 编辑工具链（create_draft / add_video / add_text / save_draft） | E | P1 |
| S04-004 | 渲染工具（render / render_status） | E | P1 |
| S04-005 | 草稿上下文关联（draft_id 贯穿多轮对话） | E | P1 |

| R03 | 脚本/程序调用方 | 通过 curl/HTTP 脚本 POST `/api/chat`，程序化驱动对话式生产线（如批量为素材配标题并渲染） |

### 1.4 系统边界

```
        R01 浏览器对话面板(S07-005)   R03 curl/脚本
                  │  POST /api/chat {message, draft_id?, asset_paths?}
                  ▼
        ┌──────────────────────────────────┐
        │  S04 对话式生产（render_server 内） │
        │  SSE 流式响应 + 工具编排           │
        └───┬──────────┬─────────┬─────────┘
            │ Function Calling（流式）
            ▼
      EXT-02 通义千问 qwen3.7-plus（REST，OpenAI 兼容/dashscope）
            │ LLM 决策的工具调用
            ├─→ S01-006  /api/assets            （资源清单）
            ├─→ S02-007  /api/perceive/cached   （VLM+ASR 分析缓存）
            ├─→ S05-001  /create_draft          （建草稿，产 draft_id）
            ├─→ S05-006  /add_video             （加视频轨道）
            ├─→ S05-009  /add_text              （加文字/标题）
            ├─→ S05-002  /save_draft            （草稿落盘）
            ├─→ S06-002  /render/draft/<id>     （提交渲染，产 task_id）
            └─→ S06-005  /render/status/<id>    （渲染状态轮询）
```

边界约定：
1. S04 不落任何持久化存储——会话上下文为内存态（与全项目"无关系型数据库"的存储形态约定一致）；
2. S04 不直接操作剪映（EXT-01）、不直接调用 FFmpeg（EXT-05）、不直接访问 ASR（EXT-03），一切经 S01/S02/S05/S06 的端点间接完成；
3. 唯一外部依赖为 EXT-02（LLM/VLM 云服务），其 API Key 需从硬编码迁移至环境变量（_metadata.md 密钥安全要求，影响 S04/S02）。

## 二、功能需求

### 2.1 对话通道

#### S04-001 SSE 流式对话（/api/chat）

##### 一、功能综述

本功能点是 S04 的统一入口，提供 `POST /api/chat` 端点：接收用户自然语言消息及可选的草稿/素材上下文，将对话连同工具清单交给 EXT-02 通义千问进行 Function Calling 推理，并以 SSE 流式协议实时回传四类事件——助手文字增量、工具调用记录、草稿 ID、流结束标记。用户在对话面板逐字看到 AI 回复的同时，可看到"正在调用 add_text"等工具执行过程，实现"边说边做"的透明化生产体验。

该功能解决的业务问题：传统视频编辑需要用户逐个面板操作（选素材、建草稿、加轨道、提交渲染），本功能把全部操作收敛为一次自然语言请求；SSE 流式返回避免长任务（LLM 推理 + 多次工具往返）期间的界面阻塞与请求超时。

与上下游的关系：上游为 S07-005 对话面板或 R03 脚本；下游为 S04-002~004 的 9 个对话工具（见 S04-002/003/004 展开），工具再下探至 S01/S02/S05/S06 端点。

| BO-04-002 | SSE 事件 | event_type | VARCHAR | 12 | Y | text / tool / draft_id / done | 4 种事件枚举 |

| | | parameters_schema | TEXT(JSON) | - | Y | JSON Schema 格式入参定义 | 供 LLM 生成 args |

> 数据类型遵循 _metadata.md 数据类型约定（LLM 消息 TEXT、文件路径 VARCHAR(260)、草稿ID VARCHAR(36) 等）。

##### 三、业务活动

1. **接收请求**：校验 `message` 非空；解析可选 `draft_id`（须为已存在草稿）与 `asset_paths`（须为 render_uploads/ 下合法路径）。
2. **组装对话上下文**：将系统提示词、会话历史（含 draft_id 上下文，见 S04-005）、9 个工具定义、用户消息组装为 LLM 请求。
3. **建立 SSE 通道**：以 `Content-Type: text/event-stream` 响应，进入流式转发循环。
4. **流式转发**：LLM 每产出一小段文字即推送 `data: {"text": "..."}`；LLM 每发起一次工具调用，先执行工具（经 S01/S02/S05/S06 端点），再将调用名/入参/结果打包推送 `data: {"tool": "...", "args": {...}, "result": {...}}`；`create_draft` 成功后推送 `data: {"draft_id": "..."}`；全部推理结束推送 `data: [DONE]` 并关闭流。
5. **异常处理**：LLM 调用失败、工具执行异常时，以文字事件返回错误说明，仍保证 `[DONE]` 收尾，避免客户端挂起。

##### 用例 U-04-001-01 发起流式对话生产

| 项目 | 内容 |
|------|------|
| 用例编号 | U-04-001-01 |
| 用例名称 | 发起流式对话生产 |

**功能要求：**

| 类型 | 描述 |
|------|------|
| 基本功能 | 共计 6 个基本功能点：|
| | 1. 接收并校验 POST /api/chat 请求（message 必填、draft_id/asset_paths 可选） |
| | 2. 组装含 9 个工具定义的 LLM 请求并调用 EXT-02 流式接口 |
| | 3. 按四种事件格式流式推送：`{"text"}` / `{"tool","args","result"}` / `{"draft_id"}` / `[DONE]` |
| | 4. 工具调用即时代理执行并把结果回填给 LLM 继续推理（多轮 function calling 循环） |

**处理逻辑：**
1. 客户端 POST `/api/chat`，服务端校验入参；
2. 组装 system prompt + 会话历史（若带 draft_id 则注入草稿上下文）+ tools 清单 + 用户消息；
3. 调用 EXT-02 流式接口，逐 chunk 转发为 `data: {"text": "..."}`；
4. 收到 LLM 工具调用决策 → 按 parameters_schema 执行对应端点（S04-002~004）→ 推送 `data: {"tool", "args", "result"}` → 将结果回填 LLM 继续推理，循环直至 LLM 给出最终文字；
5. 若本轮新建草稿，推送 `data: {"draft_id": "<uuid>"}`；
6. 推送 `data: [DONE]`，结束响应。

**约束条件：**
1. SSE 为单向服务端推送，客户端不得在流中插话，新输入须发起新的 POST 请求；
2. 单次对话的工具调用链路依赖 EXT-02 网络 RTT，整体时长可能达数十秒，客户端须设置不短于 300s 的读超时或不设读超时；
3. 客户端中途断开时，服务端应终止后续工具调用，避免孤儿渲染任务；
4. 工具清单固定为 9 个（S04-002 三个 + S04-003 四个 + S04-004 两个），不在请求中动态增删。

### 2.2 感知查询工具

#### S04-002 资源查询工具（list_resources / get_resource_detail / get_transcript）

##### 一、功能综述

本功能点向 LLM 提供三个只读查询工具，使对话具备"看得见素材"的能力：`list_resources` 列出素材库全部已上传资源；`get_resource_detail` 查询单个资源的完整感知结果（VLM 画面分析 + ASR 转录 + 元数据）；`get_transcript` 单独取语音转录（含词级时间戳）。LLM 在收到"帮这个视频配标题"这类指令时，先经这些工具了解视频内容、情绪、亮点与台词，再决策后续编辑动作，避免"盲编"。

三个工具均为 S01/S02 已有能力的对话侧代理：资源清单来自 S01-006 素材库扫描（/api/assets），详情与转录来自 S02-007 感知 API 的缓存查询（/api/perceive/cached），全程零磁盘 IO、不触发重新分析，保证对话响应速度。

##### 二、业务对象

| 编码 | 业务对象 | 数据项 | 数据类型 | 长度 | 必填 | 编码引用说明 | 备注 |
|------|---------|--------|---------|------|------|------------|------|
| BO-04-004 | 资源项（清单行） | resource_path | VARCHAR(路径) | 260 | Y | 引用 S01 render_uploads/ 素材 | 唯一标识 |
| | | resource_type | VARCHAR | 5 | Y | video / image / audio | S01-005 自动分类结果 |
| | | file_size | INT | MB | N | 引用 S01 素材属性 | 供 LLM 判断可用性 |
| | | md5_key | VARCHAR(MD5) | 32 | N | 引用 S01-008 内存缓存键 | 已分析标记 |
| | | analyzed | 布尔 | 1 | Y | true=已有感知缓存 | 决定详情工具可用性 |
| BO-04-005 | 资源详情（感知结果） | resource_path | VARCHAR(路径) | 260 | Y | 同上 | |
| | | duration | DECIMAL | (10,3) | N | _metadata_ 视频时长，秒 | ffprobe 提取 |
| | | width / height | INT | 4 | N | 默认画布 1080×1920 | |
| | | fps | DECIMAL | (5,2) | N | | |
| | | scene_segments | TEXT(JSON) | - | N | 引用 S02-002 场景检测 start/end 秒 | |
| | | vlm_analysis | TEXT(JSON) | - | N | 引用 S02-003 VLM 分析（内容/情绪/质量/亮点/帧内文字） | 长文本 |
| | | transcript | TEXT(JSON) | - | N | 引用 S02-004 ASR 词级时间戳转录 | get_transcript 单独取此字段 |

##### 三、业务活动

1. **list_resources**：LLM 调用（无必填入参）→ 代理 GET `/api/assets` → 返回 BO-04-004 清单。

### 2.3 编辑工具链

#### S04-003 编辑工具链（create_draft / add_video / add_text / save_draft）

##### 一、功能综述

本功能点向 LLM 提供四个草稿编辑工具，覆盖"从零建片"的最小闭环：`create_draft` 创建空白剪映草稿并获得 draft_id；`add_video` 向时间线添加视频轨道素材（可带转场/蒙版/变速/音量）；`add_text` 添加标题/文字（可指定字体/颜色/阴影/背景/动画）；`save_draft` 把编辑结果落盘为剪映草稿文件夹。四者由 LLM 按"先建、再添、后存"的顺序自主编排，是"一句话成片"的核心执行机构。

四个工具是 S05 草稿编辑服务（VectCutAPI 28 端点中的 4 个核心写端点）的对话侧代理：create_draft→/create_draft（S05-001）、add_video→/add_video（S05-006）、add_text→/add_text（S05-009）、save_draft→/save_draft（S05-002）。S04 不实现任何草稿文件逻辑，仅做参数透传与结果（尤其 draft_id）的会话绑定。

### 2.4 渲染工具

#### S04-004 渲染工具（render / render_status）

##### 一、功能综述

本功能点向 LLM 提供两个渲染工具，把无人值守渲染能力接入对话：`render` 对已保存草稿提交渲染任务（异步，立即返回 task_id，任务进入 S06 多桌面渲染池排队，由 Frida 驱动剪映在独立 Windows 桌面真后台导出）；`render_status` 按 task_id 查询任务状态（queued/rendering/done/error），done 后可获得成片 mp4 下载地址。用户说"渲染吧"，对话流里即可看到任务提交与状态回报，全程无需切到渲染面板。

`render` 代理 S06-002 的 `POST /render/draft/<draft_id>`（按 VectCutAPI 生成的草稿 ID 渲染）；`render_status` 代理 S06-005 的 `GET /render/status/<task_id>`。渲染是全流水线最重环节（注入剪映 → UI 合成点击 → 导出 → 完成检测），本系统刻意保持异步语义，避免 SSE 长阻塞。

##### 二、业务对象

| 编码 | 业务对象 | 数据项 | 数据类型 | 长度 | 必填 | 编码引用说明 | 备注 |
|------|---------|--------|---------|------|------|------------|------|
| BO-04-007 | 渲染操作记录 | draft_id | VARCHAR(UUID) | 36 | Y | 引用 S05 草稿 ID | render 入参 |
| | | task_id | VARCHAR(Hex) | 8 | Y | 引用 S06 任务 ID（uuid hex 前 8 位） | render 出参 |
| | | status | VARCHAR | 10 | Y | queued / rendering / done / error | 引用 S06-003 状态枚举 |
| | | mp4_path | VARCHAR(路径) | 260 | N | 引用 S06 渲染输出 Videos/*.mp4 | done 后填 |
| | | submit_time | DATETIME | - | Y | 提交时间 | 内存会话态 |

##### 三、业务活动

1. **render**：LLM 调用（draft_id 或由会话上下文填充）→ 代理 POST `/render/draft/<draft_id>` → 返回 task_id → 记 BO-04-007 并绑定会话。

3. 渲染期间用户可继续对话（问进度、改下一件事），渲染状态以拉取方式获取。

### 2.5 会话上下文

#### S04-005 草稿上下文关联（draft_id 贯穿多轮对话）

##### 一、功能综述

本功能点维护对话会话的内存态上下文，使生产过程可以跨多轮对话连续推进：首轮 create_draft 产生的 draft_id 经 SSE `{"draft_id":...}` 事件告知前端并绑定会话；此后用户在同一会话中继续说"再加一行副标题"、"把标题改成黄色"、"直接渲染"，LLM 的每次工具调用无需用户重复报草稿号，服务端以会话当前 draft_id（及最近 task_id）自动补全。用户也可在新请求中显式携带 draft_id 续编历史草稿（如在剪映草稿管理里看中的旧草稿）。

该功能是对话式生产从"一次性指令"升级为"连续创作"的关键：把"建草稿 → 改草稿 → 渲染 → 再改 → 再渲染"串成一条以 draft_id 为轴的上下文链。会话状态为纯内存字典（线程锁保护），不落盘，服务重启即清空——与全项目"无关系型数据库"的存储形态一致。

##### 二、业务对象

| 编码 | 业务对象 | 数据项 | 数据类型 | 长度 | 必填 | 编码引用说明 | 备注 |
|------|---------|--------|---------|------|------|------------|------|
| BO-04-008 | 会话上下文 | session_id | VARCHAR | 32 | Y | 服务端生成/前端携带的会话标识 | 内存态 |
| | | draft_id | VARCHAR(UUID) | 36 | N | 引用 BO-04-006/007 | 当前绑定草稿，null=未建 |
| | | task_id | VARCHAR(Hex) | 8 | N | 引用 BO-04-007 | 最近渲染任务 |
| | | history | TEXT(JSON) | - | Y | LLM messages 数组（user/assistant/tool 序列） | 供多轮推理 |
| | | asset_paths | VARCHAR(路径) | 260×N | N | 引用 BO-04-004 | 会话内关注的素材 |
| | | turn_no | INT | - | Y | 当前轮次号，从 1 递增 | |

##### 三、业务活动

1. **绑定**：create_draft 成功 → draft_id 写入会话上下文 + 推送 draft_id 事件；render 成功 → task_id 写入上下文。
2. **补全**：后续轮次 LLM 工具调用缺 draft_id/task_id 参数时，服务端以会话当前值自动填充再执行。
3. **续编**：POST /api/chat 显式携带 draft_id → 服务端校验草稿存在后绑定为新上下文（切换草稿），可继续 add_text 等编辑。
4. **更新**：每轮对话的 user 消息、assistant 回复、tool 调用序列追加进 history，供 LLM 多轮推理。
5. **失效**：会话超时或服务重启，上下文清空；携带的 draft_id 指向已删除草稿时拒绝绑定并提示。

##### 用例 U-04-005-01 多轮对话续编同一草稿

| 项目 | 内容 |

| 用例名称 | 多轮对话续编同一草稿 |
| 业务说明 | 第 1 轮"建草稿加视频加标题并渲染"，第 2 轮"再加一行副标题，再渲染一次"，第 3 轮"刚才那个渲染好了吗"——三轮共用同一 draft_id/task_id 上下文 |
| 规范引用 | 无 |

| 类型 | 描述 |
|------|------|
| 基本功能 | 共计 5 个基本功能点：|

**处理逻辑：**
1. 收到请求 → 按 session（或请求特征）定位会话上下文；
2. 显式 draft_id：校验并绑定；未带且会话已有：沿用；均无：由 LLM 决策是否 create_draft；
3. 组装 history + 上下文摘要（当前 draft_id/task_id/asset_paths）注入 LLM；
4. 工具执行时补全缺失的 draft_id/task_id；
5. 轮末更新 history、turn_no，必要时更新 draft_id/task_id 绑定。

**状态流转（会话草稿绑定态）：**

| 当前状态 | 事件 | 目标状态 | 前置校验 | 后置动作 |
|---------|------|---------|---------|---------|
| 未绑定 | create_draft 成功 | 已绑定(draft_id) | 编辑服务可用 | 推送 {"draft_id"} 事件、记 BO-04-006 |
| 已绑定 | 再次 create_draft 成功 | 已绑定(新 draft_id) | — | 覆盖绑定、推送新 draft_id 事件 |
| 未绑定 | 请求携带 draft_id | 已绑定 | 草稿存在于剪映草稿目录 | 注入 LLM 上下文 |
| 已绑定 | 请求携带另一 draft_id | 已绑定(切换) | 同上 | 提示切换 |
| 已绑定 | 草稿被删除（S07-008） | 失效 | 下次工具调用校验失败 | 返回 error，由 LLM 引导重建 |

**约束条件：**
1. 会话上下文仅存内存，容量与生命周期受 render_server 进程约束，不做持久化与跨服务共享；
2. 并发多会话（多浏览器页签）上下文相互隔离，不得串草稿；
3. history 随轮次增长，须控制送入 LLM 的消息规模（超长时截断早期轮次、保留最近工具结果），防止 token 超限。
