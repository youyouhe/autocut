## 一、系统概述

### 1.1 系统定位

S02 视频感知与质检是 AI 视频工作台的"眼睛与耳朵"，位于生产流水线的第二环节：素材经 S01 素材接入与缓存管理进入素材库后，由本系统完成"看懂视频内容 + 听懂音频 + 检查渲染结果"三层感知（对应实现载体 perceive.py，手册 §9）。

系统以 `perceive_video` 四步流水线为核心（元数据提取 → 场景检测 → 抽帧+VLM 画面分析 → ASR 语音转录），将非结构化的视频文件转化为结构化的感知结果 JSON（meta/scenes/visual_analysis/audio），供下游 S03 模板引擎选片、S04 对话式生产（get_resource_detail/get_transcript 工具）、S08 MCP 感知工具消费；同时以 `perceive_result` 渲染质检对 S06 无人值守渲染的成片进行 8 帧 VLM 打分，形成"渲染 → 质检"质量闭环。

### 1.2 业务范围

| 功能域 | 功能点 | 内容 |
|--------|--------|------|
| 2.1 视频结构感知 | S02-001~002 | ffprobe 元数据提取、FFmpeg scene 滤镜场景检测 |
| 2.2 智能内容理解 | S02-003~005 | 均匀抽帧+通义千问 VLM 画面分析、自建 ASR 词级时间戳转录、ASR 响应多格式解析归一化 |
| 2.3 质检与感知服务 | S02-006~007 | 渲染成片 8 帧 VLM 质检打分、4 个感知 REST 端点（路径分析/缓存查询/上传分析/质检） |

## 二、功能需求

### 2.1 视频结构感知

#### S02-001 视频元数据提取（ffprobe：时长/分辨率/帧率）

##### 一、功能综述

任何感知活动的第一步都是建立视频的"结构档案"。素材入库（S01）或按路径分析被调用后，系统通过 FFprobe（EXT-05）读取视频容器与流信息，提取时长、宽、高、帧率四项核心元数据，形成 meta 对象。

meta 是后续所有感知步骤的基准：场景检测的切点时间以 duration 为上限校验、抽帧的均匀抽样以 duration 为区间、ASR 的音频提取以视频文件为输入、质检的 duration_ok 比对以成片 duration 为依据。元数据随整体分析结果落入 analysis_cache JSON 缓存，重复分析同一素材时 O(1) 命中，不重复调用 ffprobe。

##### 二、业务对象

| 编码 | 业务对象 | 数据项 | 数据类型 | 长度 | 必填 | 编码引用说明 | 备注 |
|------|---------|--------|---------|------|------|------------|------|
| BO-02-001 | 视频元数据 meta | source_path | VARCHAR | 260 | Y | S01 素材库 / 上传临时文件路径 | Windows MAX_PATH 约定 |
| | | duration | DECIMAL | (10,3) | Y | ffprobe format.duration | 秒，毫秒精度 |
| | | width | INT | 4 | Y | ffprobe video stream | 像素，横屏/竖屏原始值 |
| | | height | INT | 4 | Y | ffprobe video stream | 像素，默认画布 1080×1920 |
| | | fps | DECIMAL | (5,2) | Y | ffprobe avg_frame_rate 换算 | 保留两位小数 |

> 数据类型遵循 _metadata.md 数据类型约定（duration DECIMAL(10,3)、分辨率 INT、帧率 DECIMAL(5,2)、文件路径 VARCHAR(260)）。

##### 三、业务活动

1. **提取**：接收视频路径，调用 ffprobe（-v error -print_format json）读取容器与流信息，解析生成 meta 对象。
2. **校验**：校验路径存在、文件可读、duration/分辨率/帧率可解析且数值合法（duration>0，width/height>0，fps>0）。
3. **缓存**：meta 作为感知结果 JSON 的组成部分，随分析结果写入内存缓存与 analysis_cache/*.json（键=路径 md5，由 S01-008 统一管理）。
4. **查询**：经 /api/perceive/cached 与 /api/memory/analysis 查询已提取的元数据摘要。

#### S02-002 场景检测（FFmpeg scene 滤镜）

##### 一、功能综述

场景检测识别视频中的镜头切换时间点，回答"这个视频由几个镜头构成、在哪里切换"的问题。系统通过 FFmpeg scene 滤镜（EXT-05）对视频帧间差异度进行计算，超过阈值的时间点被记录为场景切点，输出按时间升序排列的切点列表 scenes。

切点列表是下游智能剪辑的关键输入：S03 模板引擎与 S04 对话式生产可依据切点做镜头级选段，避免在镜头中间硬切；visual_analysis 的 highlights（精彩时间区间）也以切点为参照定位。场景检测与 VLM 分析相互独立，检测失败时降级为空列表，不阻塞整个感知流水线。

##### 二、业务对象

| 编码 | 业务对象 | 数据项 | 数据类型 | 长度 | 必填 | 编码引用说明 | 备注 |
|------|---------|--------|---------|------|------|------------|------|
| BO-02-002 | 场景切点列表 scenes | scene_count | INT | 4 | Y | 本系统计算 | 切点总数，无切换时为 0 |
| | | scene_index | INT | 4 | Y | 序号，0 起 | 按时间升序 |
| | | time_sec | DECIMAL | (10,3) | Y | scene 滤镜检测 | 镜头切换时间点，秒 |
| | | time_text | VARCHAR | 12 | N | time_sec 格式化 | 可读形式 mm:ss.s，供前端展示 |

> 时间区间遵循 _metadata.md 约定：DECIMAL(10,3)，单位秒。

##### 三、业务活动

1. **检测**：以视频为输入运行 FFmpeg scene 滤镜，收集镜头切换时间点。
2. **归一化**：切点按时间升序排序、编号，并校验 time_sec ∈ [0, duration]（duration 来自 BO-02-001）。
3. **降级**：检测失败或无显著切换时输出空列表并记录日志，不影响后续抽帧/VLM/ASR 步骤。
4. **缓存**：scenes 随整体分析结果写入缓存，与 meta 同生命周期。

| 规范引用 | 运行环境约束：FFmpeg 须在系统 PATH 中可用（_metadata.md） |

### 2.2 智能内容理解

#### S02-003 抽帧与 VLM 画面分析（内容/情绪/质量/亮点/帧内文字）

##### 一、功能综述

画面分析让系统"看懂"视频：从全时长均匀抽取 N 帧（默认 5 帧，可调），将帧图像与结构化提示词一并送交通义千问 qwen3.7-plus VLM（EXT-02），返回对视频内容的六维结构化理解——主要内容（content）、情绪氛围（mood）、画面质量评估（quality，1-10 分+理由）、精彩时间区间（highlights）、适合用途（suitable_for）、画面文字提取（text_in_frame）。

visual_analysis 是整条生产线的"语义索引"：S04 对话式生产据它回答"这段素材是什么、适合做什么"；S03 模板引擎据 suitable_for 匹配模板；S07 前端在资源详情中直接展示。它是 token 开销最大、时延最长的感知步骤，因此帧数可调（frame_count），并在 VLM/ASR 超时时建议调小帧数或跳过转录（手册 §19.4）。

##### 二、业务对象

| 编码 | 业务对象 | 数据项 | 数据类型 | 长度 | 必填 | 编码引用说明 | 备注 |
|------|---------|--------|---------|------|------|------------|------|
| BO-02-003 | 抽帧样本 frame_sample | frame_seq | INT | 4 | Y | 1..N 序号 | N=frame_count（默认 5） |
| | | time_sec | DECIMAL | (10,3) | Y | 均匀抽样计算 | 抽样时间点 = duration×(seq-0.5)/N |
| | | image_ref | VARCHAR | 260 | Y | 临时 jpg 路径 | 用后清理，不长期保存 |
| BO-02-004 | 画面分析结果 visual_analysis | content | TEXT | - | Y | EXT-02 VLM 输出 | 视频主要内容描述 |
| | | mood | VARCHAR | 200 | Y | EXT-02 VLM 输出 | 情绪氛围 |
| | | quality | VARCHAR | 500 | Y | EXT-02 VLM 输出 | 画面质量评估（1-10）+理由 |
| | | highlights | TEXT | - | N | EXT-02 VLM 输出 | 精彩时间区间，JSON 字符串数组 |
| | | suitable_for | TEXT | - | N | EXT-02 VLM 输出 | 适合用途，JSON 字符串数组 |
| | | text_in_frame | TEXT | - | N | EXT-02 VLM 输出 | 画面文字提取 |

> highlights/suitable_for 为 JSON 字符串数组，遵循 _metadata.md"长文本（转录/分析）TEXT"约定；quality 含分值与理由文本。

##### 三、业务活动

1. **抽帧**：依据 meta.duration 与 frame_count 计算均匀抽样时间点，FFmpeg（EXT-05）导出 N 张 jpg 帧图。
2. **组装提示词**：按系统固定提示词模板（手册 §9.3）要求 VLM 返回六字段结构化 JSON。
3. **调用 VLM**：多帧图像 + 提示词提交通义千问 qwen3.7-plus（OpenAI 兼容接口，dashscope）。
4. **容错解析**：VLM 返回做 JSON 容错解析；六字段缺失时按空值容错，解析彻底失败时 visual_analysis 置空并记录错误。
5. **清理与缓存**：临时帧图用后删除；visual_analysis 随整体分析结果缓存。

#### S02-004 ASR 语音转录（词级时间戳）

##### 一、功能综述

#### S02-005 ASR 响应解析归一化（JSON/SRT/包装格式兼容）

##### 一、功能综述

自建 ASR 服务的返回格式存在多种形态，且属于自建服务、格式可能随版本演化（手册 §19.4 明示"自建 ASR 返回格式变化时需扩展解析"）。本功能将 S02-004 收到的 ASR 原始响应统一归一化为标准结构 {segments:[{start,end,text}], full_text}，隔离上游格式变化对下游的冲击。

解析器兼容四种格式：① JSON 列表（元素含时间戳与文本）；② SRT 字幕文本；③ {"code","data":"<SRT>"} 包装格式（业务码包 SRT）；④ {"segments":[]} 包装格式。多格式探测按固定次序进行，命中即归一化；全部失败时保留原始响应文本供排查。归一化结果是 S02-004 的 audio 对象与 S04 get_transcript 工具的唯一数据来源。

##### 二、业务对象

| 编码 | 业务对象 | 数据项 | 数据类型 | 长度 | 必填 | 编码引用说明 | 备注 |
|------|---------|--------|---------|------|------|------------|------|
| BO-02-007 | ASR 原始响应 asr_raw | response_text | TEXT | - | Y | EXT-03 响应体原文 | 保留供失败排查 |
| | | detected_format | VARCHAR | 20 | Y | 解析器判定 | json_list / srt / wrapped_srt / segments |
| | | parse_status | VARCHAR | 10 | Y | 解析结果 | ok / failed |

> 归一化输出复用 BO-02-005/BO-02-006（segment 与 audio），不另设对象。

##### 三、业务活动

1. **格式探测**：按 json_list → segments 包装 → wrapped_srt → srt 的次序尝试解析原始响应。
2. **归一化**：命中格式后转换为标准 segments（start/end/text，秒、三位小数）并拼接 full_text。
3. **失败保留**：全部格式解析失败时置 parse_status=failed，保留 response_text 供扩展解析。
4. **可扩展**：新增格式分支时不影响既有格式（对应"格式变化时需扩展解析"的运维要求）。

### 2.3 质检与感知服务

#### S02-006 渲染质检（抽 8 帧 VLM 打分：quality_score/issues/suggestions）

##### 一、功能综述

渲染质检是生产线的最后一道质量闸门。S06 无人值守渲染输出成片后，本功能对成片均匀抽取 8 帧，连同调用方提供的质检期望（expectations，可选）一并送通义千问 VLM（EXT-02）打分，返回质量分（quality_score，0-10）、问题清单（issues）、时长是否符合期望（duration_ok）、改进建议（suggestions）四项质检结论。

与 S02-003 的画面分析不同，质检的输入是"系统自己生产的成片"，评估对象是渲染正确性（时长、画面完整性、内容要素），而非素材价值。质检结果供 R01 决定是否重新渲染、供 R02/R03 的自动化流水线做质量门禁。质检固定 8 帧、与感知分析的 frame_count 相互独立。

##### 二、业务对象

##### 三、业务活动

1. **抽帧**：对成片（mp4）均匀抽取固定 8 帧（FFmpeg，EXT-05）。
2. **期望装配**：解析调用方 expectations（时长区间/必需要素），无则跳过相应比对。
3. **VLM 打分**：帧图+期望提交 EXT-02，获取分值、问题、建议。
4. **结论计算**：成片 duration 与期望区间比对得出 duration_ok；分值、问题、建议装配为质检结果。
5. **结果返回**：经 /perceive/result 返回；调用方（R01/R02/R03）据此决定收货或重渲染。

#### S02-007 感知 API（路径分析/缓存查询/上传分析/质检端点）

##### 一、功能综述

感知 API 是本系统对外的统一服务面，将 S02-001~006 的能力封装为 4 个 REST 端点（基址 http://localhost:9002，手册 §16.2）：POST /api/perceive（按路径分析，缓存优先，支持 force/do_asr/frames 参数）、GET /api/perceive/cached（仅查缓存，不读磁盘）、POST /perceive/video（multipart 上传文件直接分析）、POST /perceive/result（multipart 上传成片做质检）。

端点层承担三件事：参数校验与透传（force/do_asr/frames/expectations）、缓存策略执行（默认走 S01-008 分析元数据缓存的 md5 键 O(1) 命中，force=true 强制重分析并更新缓存）、结构化错误返回（错误须含阶段与原因，对应 §19.4 感知故障排查）。R01 经 S07 前端、R02 经 S08 MCP 工具、R03 经脚本分别触达这 4 个端点。

##### 三、业务活动

1. **路径分析**：POST /api/perceive 校验 path → 缓存探测（md5 键）→ 未命中或 force=true 时执行四步流水线 → 结果写缓存并返回。
2. **缓存查询**：GET /api/perceive/cached 按 path 查内存缓存，不读磁盘、不触发分析；未命中返回未命中标识。
3. **上传分析**：POST /perceive/video 接收 multipart 文件与 do_asr/frames 表单，对上传文件执行感知流水线。
4. **上传质检**：POST /perceive/result 接收 mp4 与 expectations，调用 S02-006 质检。
5. **错误处理**：各端点错误统一结构化返回（阶段+原因），支撑 §19.4 排查（VLM/ASR 超时、格式不识别等）。
