## 一、系统概述

### 1.1 系统定位

S01 素材接入与缓存管理是 AI 视频工作台生产流水线的"入口与底座"。系统定位为：面向手机、电脑、浏览器、脚本四类来源的**素材统一接入层**，以及面向下游感知（S02）、生产（S03/S04）、编辑（S05）的**内存缓存与素材库服务层**。

系统实现两条素材接入通道：其一为 **LocalSend v2.2 协议接收端**（localsend_recv.py），使安装了官方 LocalSend App 的手机/电脑可以在局域网内直接向本工作台发送视频/图片/音频素材，无需安装额外客户端；其二为 **Web 文件上传通道**（/api/upload），供浏览器 Web GUI 与自动化脚本以 multipart 表单方式上传素材。两条通道的素材统一落盘到 `render_uploads/` 素材库目录，形成单一素材池。

在接入层之上，系统提供两级内存缓存（memory_store.py）：**视频字节缓存**（≤50MB 视频按需载入 RAM，总上限 500MB、LRU 淘汰，使 /api/video/serve 命中时零磁盘 IO）与**分析元数据缓存**（以素材路径 md5 为键、O(1) 字典查询，启动时全量载入 analysis_cache/*.json）。两级缓存显著降低重复分析、重复预览的性能开销，是全流水线响应速度的基础保障。

### 1.2 业务范围

本系统业务范围涵盖三个功能域：

| 功能域 | 功能点范围 | 业务内容 |
|--------|-----------|---------|
| 素材接入（LocalSend 通道） | S01-001 ~ S01-004 | UDP 多播设备发现、v2.2 协议上传传输（prepare-upload/upload 流式接收）、会话管理（单活跃会话/SHA256 校验/同名序号）、接收端按需启停与状态查询 |
| 素材接入（Web 通道）与素材库 | S01-005 ~ S01-006 | Web multipart 文件上传与自动分类（video/image/audio）、render_uploads/ 素材库全量扫描 |
| 缓存管理 | S01-007 ~ S01-009 | 视频字节内存缓存（≤50MB 入 RAM、LRU 500MB、X-From-RAM 响应头）、分析元数据缓存（md5 键 O(1) 查询）、内存与统计查询 API |

不属本系统范围：素材的智能分析（S02 视频感知与质检）、素材进入草稿与渲染（S05/S06）、前端 GUI 面板交互（S07-003 素材面板 / S07-004 LocalSend 接收对话框仅作为本系统 REST API 的调用方）。

```
└──────────────────────────────────────────────────────┘
   │ 文件落盘            │ REST (port 9002)              │ 内存读取
   ▼                    ▼                               ▼

 analysis_cache/     R03 脚本 (/api/video/serve,       (/api/perceive
 (本地文件系统)       /api/memory/*, /api/localsend/*)   缓存优先)
```

边界约定：
- **北向（上游）**：EXT-04 LocalSend 客户端（UDP 多播 + HTTP v2.2）、R01/R02/R03 的 REST 调用；
- **南向（下游）**：本地文件系统（render_uploads/ 素材目录、analysis_cache/ 分析缓存目录），S02 感知服务读写分析缓存；
- **协议边界**：LocalSend 接收端独立监听 **53317** 端口（UDP 多播 + 明文 HTTP），与主服务 9002 端口解耦；接收端**按需启停，不随主服务常驻**；
- **不越界**：本系统不做媒体内容解析（FFprobe/VLM/ASR 属 EXT-05 与 S02 范围），不做用户鉴权（本地单机部署）。

## 二、功能需求

### 2.1 素材接入 — LocalSend 通道（S01-001 ~ S01-004）

本功能域实现 LocalSend v2.2 协议接收端（localsend_recv.py），让手机/电脑用官方 LocalSend App 直接往本工具发素材，覆盖"设备发现 → 上传传输 → 会话管理 → 接收端启停"完整链路。

#### S01-001 LocalSend 设备发现（UDP 多播 announce）

##### 一、功能综述

LocalSend 官方客户端依靠 UDP 多播发现局域网内的接收设备。本功能让 AI 视频工作台在局域网中以"AI 视频工作台"设备身份被手机/电脑的 LocalSend App 搜索到，是 LocalSend 素材接入通道的第一环。接收端启动后，系统向多播组 **224.0.0.167:53317** 周期发送 announce 广播报文：启动时连发 3 次以加快邻居收敛，此后每 30 秒重复一次，维持设备在客户端侧的持续可见性。

本功能重点解决 Windows 多网卡环境下的"手机发现不到设备"问题。Windows 主机常同时存在 WSL/Hyper-V 虚拟网卡、WLAN/以太网、蓝牙、WireGuard 等多块网卡，操作系统默认多播出口往往指向虚拟网卡，导致 announce 报文从未到达手机所在的物理局域网。系统通过 `_detect_outbound_ip()` 探测本机全部网卡 IP 并打分（优先 `192.168.x` 家庭/热点局域网段；降权 `172.x` 段（WSL/Docker 常用）；降权 `10.0.0.3`（WireGuard 常用）），选定最优出口 IP 后，以 `IP_MULTICAST_IF` 套接字选项显式固定多播发送网卡。

设备发现与上传传输（S01-002）是"广播—连接"关系：announce 仅负责宣告存在与端口，实际文件传输走明文 HTTP 53317 端口的 v2.2 端点。发现功能随接收端 `start_server()` 启动、随 `stop_server()` 停止，按需运行、不常驻。

##### 三、业务活动

1. **设备身份构造**：接收端启动时组装设备信息（BO-01-001），生成/复用设备 fingerprint；
2. **多播出口网卡探测与打分**：`_detect_outbound_ip()` 枚举本机网卡 IP，按打分规则选定出口 IP（BO-01-002）；
3. **多播接口设置**：`set_multicast_interface` 以 `IP_MULTICAST_IF` 显式绑定出口 IP；
4. **周期 announce 广播**：启动连发 3 次，其后每 30s 向 224.0.0.167:53317 发送 announce；
5. **设备信息应答**：响应客户端 `GET /api/localsend/v2/info`，返回设备信息 JSON；
6. **客户端注册**：响应 `POST /api/localsend/v2/register`，登记发送设备（R05）的注册信息；
7. **广播停止**：接收端停止时终止 announce 周期任务、关闭多播套接字。

#### S01-002 LocalSend 上传传输（prepare-upload/upload 流式接收）

##### 一、功能综述

本功能实现 LocalSend v2.2 协议的文件传输服务端：发送设备（R05）在 App 中选中本工作台设备并发起发送后，系统通过两阶段端点完成接收——`POST /api/localsend/v2/prepare-upload` 准备上传（校验请求并为每个待传文件分配 fileId 与一次性 token，返回 sessionId），随后发送设备逐文件调用 `POST /api/localsend/v2/upload?sessionId=&fileId=&token=` 上传文件体，系统以**流式写盘**方式将文件落到 render_uploads/ 目录，避免大视频文件整体驻留内存。

流式接收是本功能的核心工程价值：手机拍摄的成片视频常达数百 MB，若先聚合到内存再落盘会造成峰值内存失控。系统边收边写，配合会话管理（S01-003）的 token 校验、SHA256 完整性校验（可选）与同名序号冲突处理，保证多文件批量发送（一次勾选多个视频/图片）场景下每个文件独立、有序、可校验地落盘。

上传传输完成后，文件进入素材库（render_uploads/），即可被 S01-006 素材库扫描发现、供 S02 感知分析与 S04/S05 生产使用；接收记录写入 `_received_log` 本次运行接收历史（S01-003），供前端 LocalSend 接收对话框（S07-004）展示。

#### S01-003 LocalSend 会话管理（单会话/SHA256/重名序号）

##### 一、功能综述

会话管理为 LocalSend 接收通道提供并发控制、完整性保障与冲突消解三项核心机制。LocalSend v2.2 协议要求接收端**同一时间只允许一个活跃会话**：系统维护 `_active_session` 单例，当已有会话进行中又有新发送方发起 prepare-upload 时，返回 **409 冲突**，防止多设备并发写入造成文件交错与令牌错乱。这一约束把多发送方竞争串行化，是家庭/办公局域网多人场景下数据正确性的基础。

完整性保障通过 SHA256 摘要校验实现（可选启用）：发送设备在 prepare-upload 请求中为文件声明 sha256 值时，系统在文件落盘完成后计算实际摘要比对，不一致则判定接收失败并登记校验结果，确保跨设备传输的素材逐比特无损。重名消解解决"同一素材多次发送/不同设备同名发送"的覆盖风险：落盘前检测 render_uploads/ 下同名文件，自动追加序号 `(1)`、`(2)` 直至无冲突，任何情况下不覆盖既有素材。

会话生命周期与接收历史由本功能统一维护：`_received_log` 记录本次运行的接收历史（start_server 时清空），既作为会话结算数据返回给前端（S07-004 已收列表），也作为 stop_server() 的返回值（"本次接收文件清单"）。

|------|---------|--------|---------|------|------|------------|------|
| BO-01-003 | 会话对象（_active_session） | state | VARCHAR | 10 | Y | 本系统枚举 | preparing / transferring / done / cancelled |
| BO-01-003 | 会话对象（_active_session） | requester | VARCHAR | 64 | Y | 发送设备 fingerprint（EXT-04） | 标识发送方（R05） |

##### 三、业务活动

1. **会话创建**：prepare-upload 通过单会话校验后创建 `_active_session`（state=preparing）；

7. **会话结算**：全部文件终结后关闭会话释放单例，允许下一发送方进入。

#### S01-004 LocalSend 接收端启停与状态查询

##### 一、功能综述

本功能为 LocalSend 接收端提供**按需启停**的生命周期管理与一站式状态查询。与主服务常驻不同，接收端不随 render_server.py 自动启动，而是由用户在前端素材面板（S07-003）点"接收"按钮触发 `POST /api/localsend/start` 后才启动；`POST /api/localsend/stop` 停止接收并返回本次接收的文件清单。这种设计避免了 53317 端口被用户自己安装的官方 LocalSend 桌面端长期占用导致的冲突——只有用户明确需要接收时才占用端口。

启动过程内含端口冲突防御：若 53317 端口已被官方 LocalSend（或其他程序）占用，start 返回 **409**，提示先关闭占用方。启动动作完成多播网卡选择（S01-001 的 IP_MULTICAST_IF 设置）与 announce 启动，是整个 LocalSend 通道的总开关。停止时返回本次运行的全部接收记录（_received_log 快照），并清空运行态，为下一次启动准备干净环境。

状态查询 `GET /api/localsend/status` 返回接收端全景状态：运行中/停止、设备名、端口、活跃会话、待收文件、已收列表、本机出口 IP，既驱动前端接收对话框（S07-004）的实时展示，也是运维排查"手机发现不到设备"（多播网卡错误、端口占用）的诊断入口。

6. **异常自检**：状态查询暴露本机出口 IP 与活跃会话，支持多播网卡/端口占用故障排查。

### 2.2 素材接入 — Web 通道与素材库（S01-005 ~ S01-006）

本功能域提供不依赖 LocalSend 的直连上传通道（/api/upload），并对 render_uploads/ 素材池提供全量扫描能力（/api/assets），构成"Web 上传 → 统一素材库 → 下游消费"的接入闭环。

#### S01-005 Web 文件上传（自动分类 video/image/audio）

##### 一、功能综述

Web 文件上传为浏览器用户与自动化脚本提供最直接的素材灌入通道：`POST /api/upload` 接收 multipart 表单（字段 `files` 多文件或 `file` 单文件），将上传内容统一保存到 render_uploads/ 目录，并按文件类型**自动分类为 video / image / audio 三类**。分类结果直接驱动前端素材面板（S07-003）的分区展示，也是 S02 感知服务选择分析策略（视频走 VLM+ASR、图片走画面分析、音频走 ASR）的依据。

该通道与 LocalSend 通道（S01-001~004）在落盘层完全汇聚——两者都写入 render_uploads/，形成单一素材池，供 S01-006 扫描统一管理。相比 LocalSend 的多播发现与两阶段会话协商，Web 上传是同步单请求完成，适合脚本批量（R03 经 curl 一条命令灌入）、浏览器拖拽（R01 在素材面板选择文件）等场景。

上传完成后接口返回每个文件的保存结果（原文件名、分类、保存路径），前端据此即时刷新素材列表；素材进入素材池后即可被 S01-006 扫描、S02 分析、S03/S05 引用入草稿。

#### S01-006 素材库扫描（render_uploads/ 全量素材）

##### 一、功能综述

素材库扫描是素材池的统一出口：`GET /api/assets` 全量扫描 render_uploads/ 目录，返回其中所有素材的清单（文件名、类型、路径、大小、修改时间），供前端素材面板（S07-003）列表展示、对话式生产（S04 list_resources 工具）、外部 Agent（R02 经 S08）等所有下游消费方获取"当前系统里有什么素材"。

素材池是两条接入通道（LocalSend 落盘 S01-002、Web 上传落盘 S01-005）的物理汇聚点。扫描以目录现状为唯一事实来源：无论是哪条通道、哪次运行写入的文件，只要存在于 render_uploads/ 即被列出，从而天然弥补 LocalSend 接收历史 _received_log"仅本次运行"的局限——跨运行的素材全集始终可经扫描获得。

### 2.3 缓存管理（S01-007 ~ S01-009）

本功能域由 memory_store.py 实现两级内存缓存（视频字节缓存 + 分析元数据缓存）及统计查询 API，优化重复预览与重复分析场景的性能，是全流水线响应速度的底座。

#### S01-007 视频字节内存缓存（≤50MB 入 RAM，LRU 500MB）

##### 一、功能综述

视频字节缓存解决视频预览场景的重复磁盘 IO 问题。前端素材面板每次预览视频都会经 `GET /api/video/serve?path=` 拉取视频字节，若无缓存则每次预览都从磁盘完整读取。系统对**不超过 50MB** 的视频执行"按需载入内存"策略（`maybe_load_video`）：首次访问时读入 `_video_store` 内存字典，再次访问直接从内存返回，实现命中时**零磁盘 IO**，并通过响应头 `X-From-RAM: true` 向调用方明示本次数据来源。

内存占用以**总上限 500MB** 控制：超限时按 **LRU（最久未访问优先）** 策略淘汰缓存条目（`_evict_oldest_video`），保证内存占用有界。50MB 单文件阈值与 500MB 总上限共同构成"小视频常驻内存秒开、大视频走磁盘流式"的分级策略——超过 50MB 的大视频不进入内存，仍由磁盘直接流式服务，避免单文件挤占整个缓存预算。

该缓存与 S02 感知流水线协同：分析产生重复读取的视频同样受益于缓存命中；缓存键为素材路径的 md5（32 位十六进制串），与素材库（S01-006）返回的 path 天然衔接。

| 编码 | 业务对象 | 数据项 | 数据类型 | 长度 | 必填 | 编码引用说明 | 备注 |
|------|---------|--------|---------|------|------|------------|------|

| BO-01-008 | 视频字节缓存条目（_video_store） | video_path | VARCHAR | 260 | Y | 引用 BO-01-007.path | 原始素材路径 |

##### 三、业务活动

1. **按需载入**：/api/video/serve 请求到达且缓存未命中时，`maybe_load_video` 判定文件 ≤50MB 则读入内存（BO-01-008）；
2. **命中返回**：请求命中缓存时直接从内存返回字节，零磁盘 IO，响应头 `X-From-RAM: true`；
3. **未命中直读**：超过 50MB 的文件不入缓存，由磁盘流式服务；
4. **LRU 淘汰**：载入后总占用超 500MB 上限时，`_evict_oldest_video` 淘汰最久未访问条目直至回到限内；
5. **访问刷新**：每次命中刷新条目 last_access，维持 LRU 语义；
6. **统计暴露**：缓存状态经 S01-009 /api/memory/stats 暴露（videos_in_ram/ram_used_mb/ram_limit_mb）。

#### S01-008 分析元数据缓存（md5 键 O(1) 查询）

##### 一、功能综述

分析元数据缓存解决视频智能感知（S02：VLM 画面分析 + ASR 转录 + 元数据提取）结果的可复用问题。一次完整感知需调用云服务 VLM（EXT-02）与 ASR（EXT-03），耗时且产生 API 成本；同一素材被再次查询（刷新详情、对话引用、Agent 复用）时不应重复分析。系统将感知结果以**素材路径 md5 为键**存入 `_analysis_store` 内存字典，查询为 **O(1) 字典访问**（`get_analysis(path)`），彻底避免任何扫描式查找。

缓存具备**持久化与启动预热**能力：每次 `save_analysis(path, result)` 写内存的同时落盘到 analysis_cache/*.json，服务启动时全量载入磁盘缓存文件重建内存字典。因此缓存生命周期超越单次服务运行——重启后既有分析结果依旧秒级可查，只有新增/强制重新分析（force）才触发真实感知调用。`list_all_analysis()` 返回全部缓存摘要，支撑 /api/memory/analysis 列表端点（S01-009）与 S04 对话资源查询。

本缓存是 S02 感知 API 的统一后端：/api/perceive 按路径分析时缓存优先（命中直接返回），/api/perceive/cached 仅查缓存不读磁盘，分析完成后经 save_analysis 双写（内存+磁盘）。缓存键生成与视频字节缓存（S01-007）同源（路径 md5），两套缓存对同一素材形成"内容字节 + 感知结论"的互补加速。

#### S01-009 内存与统计查询（/api/memory/*）

##### 一、功能综述

本功能为两级缓存提供运行时可观测性：`GET /api/memory/stats` 返回视频字节缓存统计（videos_in_ram：内存中视频数 / ram_used_mb：已用内存 MB / ram_limit_mb：内存上限 MB）与分析元数据条目数（analysis_count），`GET /api/memory/analysis` 返回全部分析元数据列表（基于 list_all_analysis）。统计全部来自内存运行态，查询零磁盘 IO。

统计接口的价值在于：其一，让 R01/R03 用户直观掌握缓存健康度（是否逼近 500MB 上限、内存中驻留了多少视频、已积累多少分析结果），为"是否需要关注内存压力"提供决策依据；其二，/api/memory/analysis 实际上是"已感知素材全集"的清单视图，前端与 Agent 可用它快速定位"哪些素材已有分析结论、可直接复用"，避免对 S01-006 素材全集逐个试查缓存。

接口与 S01-007（视频字节缓存）、S01-008（分析元数据缓存）构成"执行—观测"配对：缓存机制在后台静默工作，统计接口把内部状态透明化。数据均取自 memory_store.py 的内存字典（_video_store / _analysis_store）聚合，不引入额外存储。

| 业务规则 | 1. GET /api/memory/stats 必须返回 videos_in_ram / ram_used_mb / ram_limit_mb / analysis_count 四项核心指标，数值取自当前内存运行态的即时快照 |
| | 2. ram_used_mb 必须为 _video_store 全部条目占用合计，ram_limit_mb 恒为 500；LRU 淘汰发生后统计必须即时反映（条目数与占用同步下降） |
| | 3. GET /api/memory/analysis 必须返回全部分析元数据条目（list_all_analysis 语义），条目含素材路径标识与感知结论摘要，可唯一定位素材 |
| | 4. 两个端点均为只读查询，不得触发缓存载入、磁盘读或任何感知分析动作 |
| 使用范围 | R01 视频创作者（观测与选材）；R02 外部 AI Agent（资源发现）；R03 脚本/程序调用方（监控集成） |
